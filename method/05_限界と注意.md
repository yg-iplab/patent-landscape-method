# 05 限界と注意

特許の出願は、会社の活動のごく一部しか映しません。
この手順で出る数字と読みを、どこまで信頼してよいか、どう書けば行き過ぎないかをまとめます。

---

## 1. 見えないもの（限界）

分析の文書には、必ず「限界」の節を置き、次を書きます。

- **公開までの遅れ**：出願は約1年半後に公開されます。直近2年の出願は、未公開分が残っています。伸び・減りの判断に使いません
- **ノウハウ・営業秘密**：特許にしない技術は見えません。出願しないという判断もあります
- **名寄せの範囲**：まとめなかった会社（未統合）、気づかなかった子会社の出願は入っていません。検索の部分一致で無関係な会社が混ざっていないかも、限られた目視確認です
- **事業の承継**：受け継いだ出願が自社の名義で出ていると、自社の出願が増えたように見えます
- **有償データベースの指標とは別物**：無料の公開データで作った近似です。母集団の範囲も計算方法も違います
- **件数は出願単位**：同じ発明を複数の国に出した場合の扱い（ファミリー）は、近似の節以外では数えていません
- **取得日の時点**：J-PlatPat の検索結果は、公開が進むと変わります。件数には出力日を添えます

## 2. 書き方の決まり

### 断定しない

- 件数は、技術の優劣や研究の力を示しません。件数の多さを、技術の水準の高さを示す言葉に言い換えません。出願の傾向と、事業の傾向を並べて示すところまでです
- 近似は近似と書きます。質の近似（ファミリーの国数、被引用）は、有償データベースの指標を再現したものではありません
- 特定の出願に評価の呼び名を付けません。重要候補は「分割・補正・ファミリーから、確かめる価値があると考えた出願」として並べ、理由を1行ずつ書きます
- 権利の有効性、他社の実施との関係、権利をかわせるかといった法的な判断には踏み込みません。この手順は、そのための分析ではありません

### 提言調にしない

分析者は、外から見える情報で考えているだけです。会社の内側の事情は知りません。

| こう書く | こう書かない（理由） |
|---|---|
| 外から見える範囲では〜と読めます | 会社の事情を外から言い切る書き方（内側を知らないため） |
| 〜ではないかと考えました。実際はどうか確かめたい | 会社がとるべき行動を指示する書き方（立場が違うため） |
| 出願が◯年から増えています（出願日・出願単位） | 件数から、力や優劣を言う書き方（件数は力ではないため） |
| 重要候補（分割・補正・ファミリーから） | 特定の出願に評価の呼び名を付ける書き方 |
| 公開情報のみ。公開前の出願・ノウハウは見えません | 限界を書かない書き方 |

### 事実・読み・仮説のラベルを付ける

`03` §6 のとおり、数字には出典と取得日を付け、事実と読みと仮説を混ぜません。

### 個人名を出さない

発明者、担当者、論文の著者の名前は、文書にも図にも出しません。人数と所属の種類（企業・大学など）までにします。
共同出願人の「社名」は公開情報なので出せますが、個人の出願人は出しません。

## 3. 他人の著作物の扱い

- 公報の本文を、長く写しません。書誌（番号・出願日・出願人）、番号、短い要約までにします
- 論文・記事の引用は短くし、出典を明記します
- J-PlatPat から出力した元の CSV は、公報の要約などを含むため再配布しません

## 4. 利用ルール

### J-PlatPat

- 「利用上のご案内」でロボットや大量の自動取得は禁止されています。この手順は、**人が画面で行う操作と同等の範囲**に限ります
- 実地の上限の目安：1回の作業で検索は10回まで、個別の公報を開くのは20件まで。検索と検索の間には、人が読む程度の間隔を空けます
- 結果一覧を、全ページ機械的に巡回しません。3,000件を超える式は使いません（`02` §2）
- CSV の出力には、ログインが要ります。ログイン、CAPTCHA、警告が出たら、そこで止めます。自動で回避しません

### 特許庁の特許情報取得API

- 番号が分かってから使います。1日あたりの利用回数に上限があります。最新の案内を見てから使います
- 1回の作業で20回程度を目安にします

### 国立国会図書館サーチ・J-STAGE

- NDLサーチは、API を使っていることを明記します。同時に何本も投げません
- 継続して使う場合は、公式の案内に沿います

### API キー

- キーは環境変数か `.env` に置き、git に入れません。画面・ログ・文書に出しません

## 5. 検査（公開の前）

書いた文書は、次の3つの目で点検します。

1. **事実の裏取り**：社名、数値、年、制度の記述を、出典に当たって確かめる
2. **論理と表記**：論理の飛び、誤字、表記のゆれ、数字の食い違い（本文・表・図の数字が一致しているか）
3. **読み手の目**：その会社の知財の担当者、知財の責任者、事業部門の人が読んだとき、引っかかる点、身構える点、受け取りやすい点（`01` §1 の「読み手の目」を使う）

出典つきの事実の訂正と誤字はその場で直します。解釈にかかわる指摘は、直す前に判断します。

### 品質のチェックリスト

- [ ] 数字ごとに出典がある（検索ログの行、有価証券報告書の頁、URL、取得日）
- [ ] 名寄せ表がある。まとめなかった会社に「未統合」と書いてある
- [ ] 件数の単位（出願／ファミリー）と日付の種類（出願日／公開日）が、図と表に書いてある
- [ ] 事実・読み・仮説のラベルがある
- [ ] 評価の呼び名、提言調、件数から力を言う書き方が無い
- [ ] 「限界」の節がある
- [ ] 個人名が無い
- [ ] 最終確認日（社名・数値）が書いてある

### リポジトリとして公開するとき

- 個人のメールアドレス、端末のパス、API キー、トークンが含まれていない
- 取得した元データ（CSV、PDF）が含まれていない
- 対象企業と関係者の個人名が含まれていない
- 公報の本文を長く写していない
- README の冒頭に、公開情報だけで作った個人の学習用の分析であり、対象企業とは関係がないことを書く
